# Control, Telegram и PostgreSQL

Все три сервиса — в `/etc/control/compose.yml`. База остаётся в существующем
томе `control_postgres-data`; `task control-deploy` её не перезапускает.

Первый запуск с машины разработчика (нужны Docker/Buildx и `docker login` с
правом записи в `kaledin170317/vpn`):

```sh
task control-publish
task telegram-publish
task control-init
```

До запуска проверьте локальные `.env` (секреты control и бота) и `.env.node`
(`DOCKERHUB_TOKEN` с правом чтения). Оба файла должны быть доступны только вам
(`chmod 600 .env .env.node`). **На сервере ничего останавливать вручную не надо**:
`control-init` скачает образы, применит миграции, остановит и отключит старые
`control.service` и `telegram.service` и запустит контейнеры. Старые файлы
на сервере автоматически не удаляются. PostgreSQL и данные сохраняются.
Перед миграциями рекомендуется сделать резервную копию БД.

Проверка на control-сервере:

```sh
docker ps --filter label=com.docker.compose.project=control
```

Следующие обновления: опубликуйте изменившийся образ (`task control-publish`
или `task telegram-publish`) и выполните `task control-deploy`. Контейнер с
неизменившимся образом и конфигурацией не пересоздаётся. Для новых версий
образы всегда публикуются под отдельными тегами `control-latest` и
`telegram-latest` одного приватного репозитория (один общий `latest` для
разных образов использовать нельзя).

Общие команды: `task publish` параллельно собирает все четыре образа, `task init`
последовательно запускает сначала ноды, затем control, а `task deploy`
параллельно обновляет ноды и control-сервер. Если ноды уже настроены и нужен
только переход control с systemd, используйте **`task control-init`**, а не
общий `task init`.

Локальная `.env` не копируется на сервер: Ansible передаёт переменные в Compose
при запуске. Уже созданные контейнеры сохраняют их при перезапуске Docker;
администратор Docker может прочитать их через `docker inspect`.

# JSON-подписка с резервированием VLESS

**«🇷🇺 Авто»: случайная живая VPN-нода → direct, без loopback.** Один балансировщик `random` выбирает для каждого нового соединения любую доступную зарубежную или RU-ноду, без приоритета страны. `fallbackTag=direct` включает прямой выход, когда проверки пометили всех кандидатов недоступными. Обе группы проверяются последовательно с интервалом `60s`; обнаружение отказа может занять больше минуты. Ноды без результатов проверки Xray пока считает доступными. Ошибка отдельного соединения сама по себе не вызывает мгновенный повтор через direct. Geo-правила direct и Google DoH сохранены. При восстановлении нод новые соединения снова идут через VPN. После deploy обновить подписку и переподключиться; повторно проверить память. Диагностический вариант без автоматического переключения сохранён в `xraySubscriptionMode(..., false)`.

Для снижения пиков памяти под нагрузкой JSON задаёт `policy.levels.0.bufferSize=4` (КБ) и фиксированное окно gRPC `initial_windows_size=65536` (байт), отключающее динамический рост окна. Это не общий лимит RAM; на ARM64 буфер 4 КБ и так является стандартным. Фиксированное окно может снижать скорость одного потока на большом RTT. DNS ядра и DNS туннеля в профиле Happ используют Google DoH `https://8.8.8.8/dns-query`, без дополнительного DNS-разрешения адреса резолвера. Эти меры требуют проверки на устройстве под нагрузкой: похожие пики обсуждаются в [Xray #5944](https://github.com/XTLS/Xray-core/issues/5944), но причина конкретного вылета без профиля памяти не установлена. Смена UDP DNS на DoH — проверяемая гипотеза, а не подтверждённое исправление утечки. Для применения нужно обновить подписку, дождаться обновления профиля и переподключить VPN. Проверить в экспортированном JSON наличие `initial_windows_size` и DoH, а в профиле Happ — `RemoteDNSType=DoH`.

Для устройства в режиме «с маршрутизацией» бот показывает дополнительную экспериментальную ссылку `/happ/device-json/{id}`. Регион устройства хранится в `devices.region` (по умолчанию `RU`). JSON содержит VLESS/REALITY-выходы сети users. Активные клиентские политики определяют прямые доменные/IP-правила, остальные соединения идут по цепочке резервирования выше. Серверные политики и mesh применяются только к трафику через VPN. Hysteria2 в JSON не входит; нужны VLESS-ноды внутри и вне региона устройства. HWID обязателен. Для режима устройства «без маршрутизации» этот JSON недоступен.

Политики маршрутизации имеют два независимых флага: `apply_to_nodes` и `apply_to_clients` (поля API `RoutePolicy`). Существующие политики после миграции остаются **только на нодах** (`true/false`). Старые API-клиенты при создании политики без этих полей тоже создают node-only правило. Политика для клиента должна явно включать `apply_to_clients` и указывать `rule_file` (клиентское правило без набора отклоняется); JSON не загружает наборы, назначенные только нодам. Миграция `0021_routing_scope` добавляет клиентскую политику `ru-direct-client` (ноды: false, клиент: true) по [ru-direct](https://github.com/kyoresuas/ru-direct); после промежуточной `0022_client_ru_lite` миграция `0023_client_ru_standard_cdn` возвращает клиентский код **`ru-standard`** и меняет только клиентские URL на `https://cdn.jsdelivr.net/gh/kyoresuas/ru-direct@release/geoip.dat` и `https://cdn.jsdelivr.net/gh/kyoresuas/ru-direct@release/geosite.dat`. Серверные политики не меняются. В JSON передаются короткие `geosite:ru-standard` и `geoip:ru-standard`; оба кода находятся в общих бинарных файлах из ветки `release`. Happ получает URL файлов в заголовке `Routing: happ://routing/onadd/...` с `UseChunkFiles: true`, чтобы передавать ядру сокращённые geo-файлы и экономить RAM. На control файлы проверяются перед выдачей подписки, но сами списки не вставляются в JSON. Для клиентских политик допускается только один общий набор URL geo-файлов; иначе подписка возвращает ошибку, чтобы не использовать неправильные базы. Полный JSON с балансировкой всё ещё может превысить лимит памяти iOS при нагрузке.

Проверь импорт в конкретной версии Happ, передачу `X-HWID` и получение geo-файлов для JSON-подписки до выдачи пользователям. Приложение не подмешивает правила Happ-профиля в полный JSON: `Routing` здесь нужен только для доставки `.dat` и DNS туннеля, решения о direct/proxy остаются в Xray JSON. Если клиент не скачал/не передал geo-файлы ядру, правила `geosite:`/`geoip:` не заработают — не включай этот вариант без проверки в Happ. В JSON и профиле туннеля задан Google DoH `https://8.8.8.8/dns-query`; RU-direct открывает реальный IP устройства соответствующим сайтам. При падении ноды действующие соединения прервутся, новые пойдут через доступную ноду после следующей проверки; если все ноды недоступны, интернет через VPN не заработает. Уже загруженный конфиг продолжит работать без control, но обновление подписки сейчас требует доступности всех нод (синхронизация профилей). Ссылка содержит ключи устройства — не публикуй её.

Имя подписки передаётся в HTTP-заголовке `Profile-Title` (самому JSON нельзя добавлять комментарии `#profile-title`). Использование трафика передаётся в `Subscription-Userinfo` из статистики устройства на нодах: RU-direct трафик в эту статистику не входит. Только JSON-подписка отправляет дату окончания **17.03.1703 23:59:59 UTC** (`expire=-8419161601`); отрицательный Unix timestamp может не отображаться в некоторых версиях Happ. Это только метаданные подписки: сервер не блокирует доступ по этой дате. `total=0` означает безлимитный объём. Правила VPN применяются к любому входу Happ/TUN; только резервный loopback имеет отдельный `inboundTag`. Если на устройстве пинг нод проходит, но после смены LTE/Wi-Fi трафика нет, сначала проверь доступность интернета на новой сети без VPN, затем обнови JSON-подписку, переподключись и проверь DNS и загрузку сайта через VPN. Пинг проверяет ноду отдельно и сам по себе не гарантирует прохождение трафика туннеля.
